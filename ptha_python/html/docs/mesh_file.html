Geometry: from SLAB to mesh

Your own mesh: --mesh-file

Instead of building the unit sources from SLAB, generate.py --mesh-file FILE uses the cells of a mesh you already have. The file gives the four corners of every cell. Steps 1 and 2 then do not use SLAB at all, and steps 3 to 9 (convergence, earthquake catalogue, logic tree, ruptures, rates, the report) run on that mesh unchanged.

At a glance

The input file

One line per cell, twelve numbers: the four corners of the cell in turn, each as longitude, latitude and depth. The corners must go round the cell, each one next to the following one. Where the ring starts, which way it goes, and the order of the lines do not matter. The bundled file, inputs_meshes/alaskaaleutians_quadrilateral_coors.dat, starts like this (depths in metres, negative down):

214.465729605253 59.8961038363627 -12430.9885537709 215.08649030082 59.1729825031043 -100 215.656666430792 59.2300001036757 -100 215.071975316661 59.9768523955977 -12692.9232869399
  • Depth units. --mesh-depth-units auto (default) reads the file as metres if any depth has an absolute value above 200, and as km otherwise. A subduction interface never reaches 200 km, so this is safe for real data. Force it with --mesh-depth-units m or km.
  • Depth sign. Detected from the median depth: depths negative below sea level and depths positive downwards are both accepted. Depths of both signs are refused, because the reader cannot tell down from up.
  • Units in the bundled file. The file is in metres with depths negative downwards. The reader reports it as 0.10 to 45.00 km: its shallowest corners sit at 0.1 km, not at the 0 km trench of PTHA18. The mesh is used as given.

What the reader detects

The reader, pyptha/mesh_file.py, does not assume any order. It works out the structure from the corners that the cells share:

  1. Top, bottom and sides of every cell. The orientation is carried from cell to cell across shared edges, so all cells agree. The depth then decides, once for the whole mesh, which pair of opposite edges runs down dip (the one with the largest depth change) and which side is the trench. A rule per cell would fail on fine meshes of flat or skewed slabs.
  2. Neighbours. Two cells are down-dip neighbours when one's bottom edge is the other's top edge. They are along-strike neighbours when they share a side edge. Corners are matched to a tolerance of 1e-6 degrees in longitude and latitude and 1 m in depth.
  3. The top row. The cells with nothing above them must form one chain along strike, and every column must be a chain of the same length.
  4. Orientation. The columns are reversed if needed, so that the fault dips to the right of the strike. This is rptha's convention, and the one the rest of the pipeline assumes.

A file that is not a complete rows x columns mesh is refused with a message that says what is wrong. The messages, by cause:

Where in the code: pyptha/mesh_file.py read_quadrilateral_mesh(). generate.py reads the file once when you run it, so a bad file stops the run before any folder is built.

What steps 1 and 2 do instead

Step 1does not read SLAB, does not find a trench and does not write contours. It records the mesh file name in data/step1_contours_info.json and stops. The figure of step 1 is not drawn.
Step 2reads the file and prints what it found. It saves data/slab2/unit_source_grid.npy, with unit_source_grid.meta.json holding the file's name (mesh_file), its SHA-256 (mesh_file_sha256) and the depth units (mesh_depth_units), and it draws figures/scratch_mesh_map.png from the cells.

This is what step 2 prints for the bundled alaskaaleutians file (the reference run):

  unit sources from the external mesh inputs/geometry/alaskaaleutians_quadrilateral_coors.dat
      mesh file: 78 along-strike x 4 down-dip = 312 unit sources, depth 0.10-45.00 km (file in m)
  mesh check: {'bowties': 0, 'degenerate': 0, 'overlap_fraction': 0.0, 'nonfinite': 0, 'total': 0, 'area_proj': 53.76164305174557}
  area 676,341 km2, mean dip 15.96 deg, cells 33.6-59.0 km along strike x 29.1-95.9 km down dip, trench depth 0.10-0.10 km

  saved grid -> <folder>/data/slab2/unit_source_grid.npy
  saved mesh figure -> <folder>/figures/scratch_mesh_map.png

The first line after the title gives the number of columns and rows, the depth range and the unit the file was read in (m or km); if the columns had to be reversed so the fault dips to the right of the strike, it adds , columns reversed so the fault dips to the right of the strike. The mesh check prints the counts of folded (bowties), collapsed (degenerate) and overlapping (overlap_fraction) cells, and total is 0 for a healthy mesh (what the defects are). The area line gives the total area, the angle-weighted mean dip, and the ranges of cell lengths, widths and trench-row depths. A mesh from SLAB prints more (the mesh-shape block, the per-unit-source statistics, the comparison with PTHA18); a mesh file does not.

Steps 3 and 5 read the saved grid data/slab2/unit_source_grid.npy, as they do for a SLAB mesh. Step 6 writes the geometry block of the input JSON with "mode": "mesh_file", the path of the copied file (mesh_file) and mesh_depth_units. Steps 7, 7b and 9 then read the mesh file again from that block each time (with the same depth units), instead of reusing the saved grid and checking a fingerprint as they do for a SLAB mesh. So if you replace the copy in inputs/geometry/, re-run step 2 as well, or steps 3 and 5 keep the old mesh. Step 9's report shows the mesh-file description in place of the SLAB contour figure.

The zone name still matters. It supplies the parameters that do not come from the mesh: the plate convergence, the earthquake catalogue window and the Berryman et al. (2015) parameters. Step 8 reads PTHA18's own run for the comparison when the zone is one of PTHA18's.

How to use it

python ptha_python/generate.py alaska --zone alaskaaleutians --folder alaskaaleutians_mesh --ptha false --rupture-size local --mesh-file inputs_meshes/alaskaaleutians_quadrilateral_coors.dat
python alaskaaleutians_mesh/steps/step_total.py

--mesh-depth-units m|km overrides the unit detection. generate.py copies the file into the run's inputs/geometry/, so the run does not depend on where the file is later.

Options that describe a SLAB mesh do not apply. Combined with --mesh-file, --cell-size strasser and --columns trench-edited or average-edited stop generate.py with a message. --discretizer, --columns trench or average, --cell-k, --clip and step1 --auto-clip are accepted and have no effect. Step 2 uses the mesh as given: it does not discretise, repair or edit anything, and it ignores the unit-source width and row count that --ptha true would read for the zone.

How to check a mesh file

  • At generate time. The file is read in full, so a file with the wrong number of columns, a hole, or mixed depth signs stops the run with the reason.
  • In step 2's log. Compare the column and row counts and the total area with what you expect from the file. The log prints the counts of folded, collapsed and overlapping cells. A non-zero count means the mesh needs a look in the figure.
  • In the figure. figures/scratch_mesh_map.png shows every cell on a map. Look for cells on the wrong side of the trench and for a trench that is not where you expect.
  • Against PTHA18. validation/validate_mesh_file.py reads the bundled alaskaaleutians file and compares its cells with PTHA18's own unit-source table for that zone. It needs PTHA18's official input, which official_ptha_data/fetch_official_inputs.py extracts. Run it from the repository root: python ptha_python/validation/validate_mesh_file.py.

Limits

  • Structured quadrilateral meshes only: rows down dip and columns along strike, with cells sharing their corners. Triangular meshes would need a different rupture builder, because the rupture rule and the HS generator work on rows and columns.
  • The mesh is used as given. If its trench is not at 0 km (the bundled file puts it at 0.1 km), or its cells are uneven, the results follow it. For uneven cells, --rupture-size local makes the ruptures follow the real cell sizes.
  • The report leaves out the SLAB-specific parts: the contour figure of step 1 and the SLAB product.
