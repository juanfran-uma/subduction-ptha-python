Geometry: from SLAB to mesh

2. --discretizer: optimal, lm and mid

The option chooses how step 2 turns the contours into cells. lm is rptha's method, as PTHA18 ran it. optimal (the default) is the same method with a safety net: it checks the mesh and repairs it only if a cell is folded, collapsed or overlapping. mid is rptha's older method, kept for comparison. This page explains what a broken mesh is, what each repair does, and how the three options differ.

At a glance

You wantUse
PTHA18's automatic mesh, repaired if it is broken (the normal case)--discretizer optimal
rptha exactly, even if the mesh is broken (for comparison or diagnosis)--discretizer lm
To see how much the orthogonal optimisation matters--discretizer mid

The choice is written into step 2 (DISCRETIZER) and into the input JSON ("discretizer"), so the engine builds the same mesh. Code: pyptha/contour_discretisation.py: discretized_source_from_contours_optimal(), discretized_source_from_contours_orthogonal() (lm), discretized_source_from_contours_mid().

What a broken mesh looks like

A mesh is unusable if any cell has no sensible area or shape, because the area, dip and length of the cells feed every rate. mesh_defects counts four kinds of defect. It works in a local flat projection (longitude multiplied by the cosine of the mean latitude) and only compares areas with each other, so the projection's scale does not matter.

Where in the code: contour_discretisation.py mesh_defects(), _cell_polygons(). This package's own check, not part of rptha.

--discretizer optimal

optimal (the default) means: rptha's own mesh, unless it is broken. It builds exactly the lm mesh, runs mesh_defects on it, and returns it unchanged if nothing is wrong. Only when the check finds a defect does it try, in order, three repairs that depart from rptha as little as possible, and it keeps the first one with no defect.

When a repair is needed

Folds come from contours whose ends are far apart along the zone: a shallow contour that reaches much further along the arc than a deep one, for example. Step 1's end cuts remove most of these before step 2 runs. When one remains, the defect check finds it, and optimal tries the repairs in turn. Its log names the one it uses, and it prints a warning if none removes every defect. A healthy mesh, which is the normal case, never reaches this path.

A broken mesh is not only a few bad cells. Its lines can run partly along the arc, so the rows are measured along longer and slanter lines, and the mean dip of the zone is biased. That is why the check exists and why the repair is part of the default.

Three other options build on optimal and keep its check: --columns average first builds rptha's mesh, then builds it again with the column count of the average rule, and each build is checked and, if broken, repaired; --columns trench-edited and average-edited apply the dip edit to the result; --cell-size strasser calls optimal again with more rows and columns until every cell meets the cap (cell size). With lm or mid, --columns average is ignored, and the dip edit and strasser are refused.

What optimal is notIt never replaces a healthy mesh by one that "scores better". "optimal" means rptha's automatic mesh, unless it is broken. Why not always trim the ends.

Where in the code: contour_discretisation.py discretized_source_from_contours_optimal(). Called by step 2 (DISCRETIZER == "optimal") and by logic_tree/run_logic_tree.py build_grid() when the input JSON says "discretizer": "optimal" and the saved grid cannot be reused.

The repairs, one by one

Both repairs attack the same cause. rptha pins the first and last down-dip lines to the contours' end points (s = 0 and s = 1 on every contour), and starts all the others at the same fraction of every contour. When the contours end at different places along the arc, equal fractions of contours of different length are at different places. The start lines are then slanted, and LM, which only improves the guess it is given, can stay in that slanted solution. Near the end, the pinned edge line can even be forced to run along the arc.

a. Nearest-point start

Same contours, same objective, same optimiser: only the starting guess of the coarsest multigrid level changes. The trench keeps evenly spaced points. For each of them, every deeper contour starts at the point nearest to it (searched over 2,000 points along that contour). Where the trench reaches beyond a deeper contour, several nearest points pile up on that contour's end; they are pushed apart by a tiny step (1e-6) so the start is valid, with the ends kept at 0 and 1.

Where in the code: _nearest_point_init_s_matrix(), used through _optimise_s_matrix(init="nearest") for the coarsest level only. Not part of rptha, and never used by lm.

b. End-aligned contours

This repair changes the input instead of the start: every contour is trimmed back to the along-strike span that all levels share. Each contour's two end points are projected onto every other contour (by the nearest of 4,000 points along it). At each end, every contour is cut at the innermost of those projections. After that, all contours start and finish on a common line across the zone, so the pinned edge lines go straight down dip like the interior ones.

Where in the code: align_contour_ends(), _arc_fraction_of(), _cumulative_km(). Not part of rptha.

c. Both, and the fallback

Repair c is b's trimmed contours with a's nearest-point start. If none of a, b, c is defect-free, the candidate with the fewest defects (rptha's own mesh is one of the candidates) is kept, ties broken by the larger area, and the log prints WARNING optimal: no repair removed every defect; using '...'. Inspect the mesh figure before trusting this zone.

Why the contours are not always end-aligned tested on PTHA18's own contours

End alignment removes folded tip cells when the shallow contours stop far from the deep ones along the zone. One could apply it to every zone, or whenever it lowers the worst edge column's badness.

When it was tested on PTHA18's own contours, where the right answer is known (PTHA18's published mesh), it moved away from PTHA18's mesh on several zones, reducing their area. Folded tips come from contours whose ends disagree, not from rptha's method: with step 1's contours (one unbroken line every 5 km, crooked ends cut) rptha's own mesh is usually clean.

So optimal keeps rptha's mesh whenever it is healthy, and uses the trimming only as a repair, after the gentler nearest-point start.

--discretizer lm

lm is rptha's method, as PTHA18's template (make_initial_downdip_lines.R) calls it, with no check and no repair: discretized_source_from_contours_orthogonal(). The name comes from the Levenberg-Marquardt optimiser. Whenever rptha's mesh has no defect, lm and optimal give the same grid. Use lm to reproduce PTHA18's automatic method strictly, or to see a broken mesh as rptha makes it.

Given PTHA18's own published contours, the Python discretiser reproduces PTHA18's published mesh. This is checked by validation/validate_against_ptha18.py (its mesh check), which needs PTHA18's official files (see Validation).

Where in the code: discretized_source_from_contours_orthogonal(); the R original is create_downdip_lines_on_source_contours_improved.

--discretizer mid

mid is rptha's older, deprecated method (create_downdip_lines_on_source_contours, used when improved_downdip_lines = FALSE). PTHA18 does not use it; it is kept only for comparison. There is no optimisation:

  1. The shallowest and the deepest contours are each resampled into the same number of evenly spaced points (one per 50 km of trench, plus one).
  2. Point i of the shallow contour is joined to point i of the deep contour by a straight (great-circle) cut, extended by a tiny fraction at both ends.
  3. Each cut is intersected with every contour to get its crossing points. If a cut crosses a contour more than once, the method stops with an error ("Non-unique contour levels"). The Python code does the same.
  4. Rows and the 3D resampling are the same as in lm.

The name is historical. rptha builds three candidate cuts ('eq_spacing', 'nearest', 'mid') but its code uses 'eq_spacing': the 'mid' line is commented out in the R source. The Python port follows the R code as it runs ('eq_spacing'); the option keeps the name mid.

Because the cuts are straight, they cross the contours obliquely wherever the zone is curved, so the cells are more slanted than with lm. Both methods cover the same surface, so the total area changes little, and the mean dip changes by a fraction of a degree, in either direction.
