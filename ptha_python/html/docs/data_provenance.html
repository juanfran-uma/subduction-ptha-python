Data provenance: what comes from where

With the default options (--ptha false and --convergence bird), every number in steps 1 to 7, 7b and 9 is derived from public sources: SLAB2.0 or SLAB1.0 (USGS), Bird (2003), the Global CMT catalogue, Berryman et al. (2015) and Strasser et al. (2010). PTHA18's own files are not opened in that path. The one PTHA18 input you can opt into is --convergence bird-griffin, which makes step 3 use PTHA18's plate-boundary table (a copy shipped in data/bird/, see below). PTHA18 is read at all only by step 8, the optional official run built for comparison, and step 9 shows that comparison from step 8's own output. This page states the claim precisely and shows how it was checked.

The one opt-in PTHA18 input: the Bird+Griffin table

data/bird/bird_griffin_traces_table.csv.zip is a copy of the plate-boundary table PTHA18 itself used, rptha's DATA/BIRD_PLATE_BOUNDARIES/sourcezone_traces_table_merged.csv.zip. It has 3805 rows: 1060 of Bird's steps that PTHA18 kept, 2645 source-zone traces with plate rates put together by Jonathan Griffin (eastern Indonesia, New Guinea and others), and 100 rows added by Gareth Davies. So it is PTHA18's work, published openly with rptha (BSD-3), not an independent public dataset like Bird (2003).

It is copied into data/bird/ so that no step has to open the rptha/ folder, which is why the check below sees no rptha/ read for this choice. Being a copy does not change where it comes from: a run with --convergence bird-griffin uses a PTHA18 input in step 3. The default, --convergence bird, does not, and gives the same convergence on the zones where PTHA18 itself used Bird's steps (zone by zone). Step 8 always uses the Bird+Griffin table, because it reproduces PTHA18's own run.

Checked by running, not only by reading the code

Reading the code shows the intent; running it shows the fact. The check below generated the kermadectonga2 folder with the default options and ran steps 1 to 7, 7b and 9 in order. Every Python process of the run loaded an audit hook (a sitecustomize.py that calls sys.addaudithook), so the hook also covers the child processes. It logged each attempt to open a file whose path contains one of rptha, official_ptha_data, sourcezone, outputs_official or _official, and each network connection:

python ptha_python/generate.py kermadec --zone kermadectonga2 --folder kermadectonga2 --ptha false
# with PYTHONPATH pointing to a folder that holds a sitecustomize.py with the hook, run each step in order:
python kermadectonga2/steps/step1_fetch_slab2.py     # ... through step6_write_input.py, then:
python kermadectonga2/steps/step7_run.py
python kermadectonga2/steps/step7b_stochastic_slip.py
python kermadectonga2/steps/step9_report.py

The result:

  • Opens of a watched path: no file of PTHA18 or rptha. Two expected hits, neither PTHA18 data: step 7b imports ptha_python/lib/hs_official_compare.py, a module of this package whose name contains "official"; and step 9 looks for outputs_official_status.txt in the folder (the status file that step 8 writes, absent in this run).
  • Network: one host only, ldeo.columbia.edu (the GCMT catalogue, step 4).

Step 8 was not part of this check: it needs R and the official_ptha_data folder, which the test copy did not include.

The audit logs an attempt to open a file before the open happens, so a read that would fail is logged too. The test copy had no rptha folder, so any read of it would have failed, and it would still have appeared in the log.

Why steps 2, 3, 5 and 6 can read PTHA18, and why they do not by default

Four steps have a code path that can read a PTHA18 value, for the --ptha true case: the width, the row count and the scaling relation of the zone, or the earthquake count and the convergence to print a comparison. Each read is behind an explicit guard on USE_PTHA, which generate.py --ptha false sets to False:

One fallback path remainsThe engine (step 7) and step 7b read the scaling relation and the rigidity from PTHA18's sourcezone_parameters.csv when the input file does not contain them. The table of convergence sources only feeds a printed note.

Step 9's report: the comparison without the read

The report can show a from-scratch-vs-PTHA18 comparison (mesh maps, convergence, GCMT count, rate curves) without step 9 ever opening a PTHA18 file itself. Every "official" path it reads resolves under the folder's own tree:

Constant in step 9Resolves to
OFFICIAL_RUN_DIR<folder>/outputs_official/
REFERENCE_DIR<folder>/outputs_official/ptha18_reference/
OFFICIAL_NC, OFFICIAL_CONV_NPY, OFFICIAL_GRID_NPY, OFFICIAL_GCMT_JSONall inside REFERENCE_DIR

Those files exist only if step 8 wrote them. Without step 8, the report says so in plain words, and steps 1-7's own numbers are shown in full: a from-scratch run is a complete result on its own, not a stub waiting on PTHA18.
